# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project state

An ASP.NET Core MVC app (started from the stock `dotnet new mvc` template) targeting **.NET 10** (`net10.0`, SDK 10.0.x), with EF Core on SQL Server and ASP.NET Core Identity (individual accounts). The solution uses the new XML solution format (`FBISDNETCore.slnx`) and contains a single project, `FBISDNETCore.MVC`. There is no test project yet.

## Commands

Run from the repository root (where `FBISDNETCore.slnx` lives), not from the `FBISDNETCore.MVC/` project folder:

```bash
dotnet build FBISDNETCore.slnx
dotnet run --project FBISDNETCore.MVC                         # http profile: http://localhost:5024
dotnet run --project FBISDNETCore.MVC --launch-profile https  # https://localhost:7272
# Visual Studio's "IIS Express" profile (the one normally used) serves https://localhost:44317 (http://localhost:59475)
dotnet watch --project FBISDNETCore.MVC                       # hot reload during development

# External sign-in credentials (not in source control); without them the provider's button stays a placeholder
dotnet user-secrets set "Authentication:Google:ClientId" "<id>" --project FBISDNETCore.MVC
dotnet user-secrets set "Authentication:Google:ClientSecret" "<secret>" --project FBISDNETCore.MVC
# EntraID: Authentication:AzureAd:TenantId / ClientId (ClientSecret optional; only for the code flow)
```

No tests exist yet. If a test project is added, register it in `FBISDNETCore.slnx` and run with `dotnet test FBISDNETCore.slnx` (single test: `dotnet test --filter "FullyQualifiedName~ClassName.MethodName"`).

## Architecture

- **Startup**: `Program.cs` uses the classic `Program.Main` style (not top-level statements). Services are registered on `builder.Services`; the pipeline is HTTPS redirection → routing → authorization → static assets → conventional route `{controller=Home}/{action=Index}/{id?}` plus `MapRazorPages()` (for the Identity UI). Exception handler (`/Home/Error`) and HSTS apply only outside Development.
- **Data — database-first only, two DbContexts on one database**: the project does not use code-first migrations; schema changes are made in SQL Server. Both contexts live in `Models/` and use `ConnectionStrings:DefaultConnection` (the `AdventureWorks2022` database on a local SQL Server instance).
  - `Models/AWDBContext` (plus the entity classes, `AWDBContextProcedures`, `AWDBContext.Functions`, `DbContextExtensions` in `Models/`) is **database-first**, generated by EF Core Power Tools from `efpt.config.json`. Files are marked `<auto-generated>` and are overwritten on re-scaffold, so put customizations in separate `partial` files (e.g. `OnModelCreatingPartial`). Its registration enables `UseHierarchyId()` and `UseNetTopologySuite()` because the model has `HierarchyId` and `Geometry` columns.
  - `Models/ApplicationDbContext` (`IdentityDbContext`) is hand-written and maps the `AspNet*` Identity tables, which already exist in the database (originally created by a since-deleted migration, so `__EFMigrationsHistory` is also present). Don't add migrations for it; if the Identity model ever changes, alter the tables in SQL to match.
- **Authentication**: `AddDefaultIdentity<IdentityUser>` + `AddRoles<IdentityRole>()` (roles are emitted as claims, so `[Authorize(Roles = "...")]` and `User.IsInRole` work) with `RequireConfirmedAccount = true` and the packaged Identity UI (Razor Pages under `/Identity/Account/...`, served from `Microsoft.AspNetCore.Identity.UI`). Only `Account/Login`, `Account/Register` and `Account/ExternalLogin` are overridden in `Areas/Identity/Pages/Account` (stock scaffolded page models, custom views styled with the `.auth-*` classes in `site.css`); every other Identity page still comes from the package. **Google** (`Microsoft.AspNetCore.Authentication.Google`) is registered in `Program.cs` only when `Authentication:Google:ClientId` and `ClientSecret` are configured (user secrets in development; the handler would otherwise throw on every request), and its Login-page button switches from placeholder to submit when `ExternalLogins` contains the `Google` scheme. **EntraID** is an OpenID Connect scheme named `AzureAD` (display name "EntraID"; the scheme name is what `AspNetUserLogins.LoginProvider` stores), registered when `Authentication:AzureAd:TenantId` and `ClientId` are set; callback path `/signin-oidc`. With no `ClientSecret` it uses the sign-in-only `id_token` flow (form_post; the app registration must have "ID tokens" enabled), with a secret it uses the authorization-code flow — only needed once the app calls downstream APIs. Both providers return to `Areas/Identity/Pages/Account/ExternalLogin.cshtml.cs` (overridden; stock scaffold plus explicit outcome branches): `OnGetCallbackAsync` is the single place where every external login's outcome is handled — provider error, missing external info, signed in, locked out, not allowed (unconfirmed email), or new user (shows the form that posts to `OnPostConfirmationAsync`, which creates and links the account). Provider-side failures would otherwise throw; each handler's `OnRemoteFailure` is set to `Program.RedirectRemoteFailureToCallback`, which redirects to that callback with `remoteError`. External login buttons live only on the Login page (Register is email/password only). The remaining Skyward button is a placeholder (`type="button"`) inside an `external-account` form that posts to `ExternalLogin`; wiring a provider means registering its scheme and turning its button into `type="submit" name="provider" value="<scheme>"`. To tell how the current user signed in, use `User.GetLoginMethod()` (`Extensions/ClaimsPrincipalExtensions.cs`) → `LoginMethods.Account` / `Google` / `EntraID`; it reads the `ClaimTypes.AuthenticationMethod` claim SignInManager adds for external logins (absent for password sign-ins, which carry `amr=pwd`). `Areas/Identity/Pages/_ViewStart.cshtml` makes those pages use the MVC layout; `Views/Shared/_LoginPartial.cshtml` renders the login/register links in the navbar. No `IEmailSender` is registered, so the confirm-email link is shown on the registration confirmation page instead of being emailed.
- **Static assets**: served via `MapStaticAssets()` / `.WithStaticAssets()` (build-time fingerprinted assets), not `UseStaticFiles()`. Client libraries (Bootstrap, jQuery, jquery-validation) are vendored under `wwwroot/lib` — there is no npm/LibMan build step.
- **Views**: Razor views under `Views/{Controller}/{Action}.cshtml`, shared layout in `Views/Shared/_Layout.cshtml`. CSS isolation is enabled (`_Layout.cshtml.css` compiles into `FBISDNETCore.MVC.styles.css`, referenced from the layout).
- **Project settings**: nullable reference types and implicit usings are enabled; hand-written code uses the block-scoped `namespace FBISDNETCore.MVC.X { ... }` form as in the template (the EF Core Power Tools output in `Models/` is file-scoped; leave it as generated).
